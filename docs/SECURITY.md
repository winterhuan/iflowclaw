# iFlowClaw 安全模型

## 信任边界

| 实体 | 信任级别 | 说明 |
| --- | --- | --- |
| 主进程 | 高 | 持有数据库、渠道客户端、配置与 IPC 执行权 |
| 主群 Agent | 中高 | 可以管理群组与任务，但仍通过 MCP/IPC 间接操作 |
| 非主群 Agent | 中 | 默认只能处理本群相关动作 |
| 外部群消息 | 低 | 视为不可信输入 |
| 容器内执行环境 | 中 | 目标是收敛权限，不等于可信 |

## 当前安全机制

### 1. 群组目录隔离

每个群组有独立路径：

- `groups/<folder>/`
- `data/ipc/<folder>/`

群组目录名会经过校验，禁止路径穿越和保留名冲突。

### 2. 主群 / 非主群权限分离

当前 IPC 层会限制：

- 非主群不能给其他群发消息
- 非主群不能管理其他群的任务
- 只有主群能注册新群组

这些限制在 `ipc.py` 的宿主侧生效，而不是只依赖 Agent 自律。

### 3. MCP 作为唯一宿主能力入口

Agent 不直接调用数据库或渠道 SDK。

它只能通过以下 MCP 工具请求宿主动作：

- `send_message`
- `schedule_task`
- `list_tasks`
- `pause_task`
- `resume_task`
- `cancel_task`
- `update_task`
- `register_group`

Claude 后端还会显式限制允许调用的工具列表。

### 4. 凭证处理

当前代码支持两类凭证路径：

- Claude：API Key 或 OAuth token
- iFlow / Agno：OpenAI 兼容 API Key / Base URL

容器模式下，代码还引入了 credential proxy，用于把 Claude 凭证通过宿主代理转发给容器内请求。

### 5. 发送者白名单

支持两种模式：

- `trigger`：限制谁能触发 Agent
- `drop`：不允许的发送者消息直接丢弃

配置位置默认为：

- `~/.config/iflowclaw/sender-allowlist.json`

## 容器相关边界

容器模式的目标是隔离 Agent 执行环境，但目前应视为“正在收敛中的安全层”，不是已经完成的沙箱系统。

当前代码里已经有：

- 容器运行入口
- 凭证代理
- 挂载白名单校验模块

但现状是：

- 挂载安全模块已存在，尚未完整接入运行主链路
- 容器构建与运行细节仍在演进
- 不能把容器模式视为完全成熟的安全边界

## 当前风险面

需要特别注意：

- 群组 `AGENTS.md` 和 skills 本质上是高权限提示词输入
- MCP 工具虽然受限，但工具参数仍来自模型输出
- 容器与直连模式并存时，权限边界会更复杂
- 文档或配置漂移会直接影响实际安全预期

## 安全建议

当前阶段建议：

- 仅在可信宿主机上运行
- 明确区分主群与非主群用途
- 不要把实验性容器能力当成完整隔离方案
- 对 `groups/`、`skills/`、`AGENTS.md` 的改动做代码审查
- 在引入额外挂载之前先完成挂载白名单链路收敛

## 后续收敛方向

- 完整接入挂载白名单校验
- 明确容器模式的最小挂载集
- 为 IPC、权限控制和容器链路补充更真实的集成测试
- 为主群管理能力补充更细粒度的审计与日志
