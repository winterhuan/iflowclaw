# iFlowClaw 设计原则与范围

## 目标

iFlowClaw 不是一个通用 Agent 平台，而是一个偏实用、偏个人化的群聊 AI 助手宿主。

当前目标：

- 在一个主进程里串起消息接入、任务调度和 Agent 调用
- 用尽量少的抽象实现多后端支持
- 对不同群组做工作目录和会话隔离
- 让 Agent 通过 MCP 获得“发消息、建任务、管群组”等宿主能力

## 当前设计原则

### 1. 单进程优先

主流程尽量都留在一个 Python 服务内：

- 渠道接入
- 数据库
- 轮询与串行队列
- 调度器
- IPC watcher
- Agent 编排

只有 Agent 自身执行会根据后端和模式拆分成 SDK 调用或容器内执行。

### 2. 群组隔离优先

不同群组之间默认隔离：

- 工作目录隔离
- 会话隔离
- IPC 目录隔离
- 任务管理权限隔离

主群是唯一的管理域入口。

### 3. MCP 工具最小闭环

Agent 不直接操作数据库或渠道 SDK，只通过 MCP 工具请求宿主动作。

当前闭环包括：

- 发消息
- 任务调度与管理
- 群组注册

### 4. 对后端差异做统一编排

通过 `AgentRunner` 抽象统一以下差异：

- system prompt 构建
- 会话 ID 续用
- model 选择
- 直连 / 容器执行
- skills 同步

### 5. 配置优先于硬编码，但不过度平台化

项目支持：

- 环境变量配置
- 每群 `agent_config`
- 每群 `AGENTS.md`
- 项目级 `skills/`

但不会为了“平台感”引入复杂控制面或配置中心。

## 当前明确范围

在范围内：

- Feishu 群聊消息处理
- 多后端 Agent 调用
- 基础任务调度
- 会话续用
- 群组级上下文注入
- 主群管理其他群

暂不在范围内：

- 多租户 SaaS 控制台
- 复杂权限中心
- 向量数据库式长期记忆系统
- 完整插件市场
- 高可用分布式部署

## 当前真实状态

代码已经从早期设计继续演化，新增了：

- `agno` 后端
- `container` 执行模式
- 凭证代理
- skills 同步机制
- 容器入口

因此，现在不应再把本项目理解为“只有 iFlow / Claude 直连”的实现。

## 实验性能力

以下能力已经进入仓库，但仍应保守使用：

- 容器执行模式
- 容器内后端切换
- 挂载安全白名单
- 更深的集成测试矩阵

这些能力的接口和方向已经成形，但仍需继续收敛实现细节。

## 文档维护原则

后续更新文档时，优先遵守以下顺序：

1. 以 `src/iflowclaw/` 的当前代码为准。
2. 如果设计稿与代码不一致，先记录“现状”，再记录“计划”。
3. 不把实验性能力写成已经稳定可用。
